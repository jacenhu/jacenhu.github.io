系统设计是 AI Infra 面试的决定性轮次。本文给出 4 道高频题的完整工作示例：需求澄清 -> 架构图 -> 核心组件 -> 权衡 -> 追问应对。每题配 ASCII 架构图，面试时可在白板画出。

技术原理见 KV Cache 核心知识体系，题点见 面经第 5 章。

通用方法论（每题都按此结构） ​

  1. 澄清需求（2-3 min）：主动问清楚规模、SLO、模型、约束。别假设。
  2. 估算（2 min）：算显存/带宽/QPS 量级，验证可行性。
  3. 架构（8-10 min）：画图，讲数据流，点出核心组件。
  4. 深挖核心组件（10 min）：调度、KV Cache、通信--这是区分度所在，结合本 Wiki 知识。
  5. 权衡与追问（5 min）：延迟 vs 吞吐、成本 vs 质量、显存 vs 算力。主动给方案。

面试官最爱追问的不是"是什么"而是"为什么这样选 / 还有什么方案 / 极限在哪"。每个选择都准备 Plan B。

题 1：设计高并发 LLM 推理服务（端到端）⭐⭐⭐⭐⭐ ​

1.1 需求澄清 ​

  • 规模：峰值 QPS 1000，平均输入 1K token，平均输出 500 token。
  • SLO：TTFT P99 < 1s，TPOT < 50ms。
  • 模型：70B（fp8 权重）+ GQA。
  • 约束：单集群 H100-80G，成本敏感，多租户。

1.2 估算 ​

  • 权重：70B × 1 byte(fp8) ≈ 70GB，单卡放不下，需 TP=2（每卡 35GB）。
  • KV Cache（GQA，n_kv=8, L=80, d_h=128, fp8）：单 token = 2×80×8×128×1 = 160KB。
  • 单请求 KV：1K+500 token ≈ 1.5K × 160KB ≈ 240MB。
  • 峰值并发：QPS 1000 × (prefill 1s + decode 500×50ms=25s) ≈ 在途请求巨大，纯 decode 并发 ~26000 条 -> KV 需 ~6.2TB。显然单机不行，必须分布式 + PD 分离 + KV 复用。

估算的目的不是精确，是暴露"单机不可行"并引出分布式架构。

1.4 核心组件深挖 ​

  • PD 分离：prefill 池 compute-bound 配高算力，decode 池 memory-bound 配大显存/带宽。prefill 算完 KV 通过 RDMA 传给 decode 池（MLA/量化压缩 KV 减传输量，与 decode 首步 overlap）。
  • 调度器：decode 池用连续批处理 + 优先级 + 抢占（低优先级 KV swap 出）；prefill 池用 chunked prefill 避免 long prompt 卡 decode。
  • KV Cache 池：PagedAttention 分页 + 前缀缓存（system prompt/文档复用）+ 量化 fp8 + 分层卸载（活跃 KV 在 HBM，冷 KV 在 DRAM/SSD）。全局池使会话多轮/多用户同文档命中即跳 prefill。
  • 多租户：显存配额 + KV 隔离 + 优先级队列 + 公平调度，防大客户饿死小客户。

1.5 权衡与追问 ​

  • "TTFT 怎么降？" -> chunked prefill + prefill 池独立 + KV 复用命中跳过 prefill。
  • "显存不够？" -> 量化(KV fp8/int4) + 卸载分层 + PD 分离按画像配比 + 前缀复用减总量。
  • "成本？" -> 大 batch 提利用率 + PD 分离 + 投机解码减步数 + 弹性扩缩。
  • "故障？" -> decode 实例滚动替换，KV 池持久化会话 KV 可恢复；权重热加载。
  • "为什么不用纯 TP 大集群一个模型？" -> TP 通信随卡数线性增，过大通信主导；PD 分离 + 池化更灵活。

题 2：设计 KV Cache 池化服务（Mooncake 风格）⭐⭐⭐⭐⭐ ​

2.1 需求澄清 ​

  • 多用户共享同一批文档/会话，最大化 KV 复用。
  • 单文档可达 100K+ token，复用价值高。
  • 低 QPS 但长上下文，prefill 成本高。

2.2 架构 ​

   请求 ──► 前缀匹配 ──► 命中?
                │ 是            │ 否
                ▼               ▼
          从 KV 池取 KV     Prefill 计算 ──► 写入 KV 池
                │               │
                └──► Decode（复用/新增 KV）──► 更新池
                                          │
                          ┌───────────────▼───────────────┐
                          │   全局 KV Cache 池（分层索引）  │
                          │  前缀树 / hash -> KV 位置       │
                          │  HBM(热) ⇄ DRAM(温) ⇄ SSD(冷)  │
                          │  LRU + 引用计数 + COW           │
                          └───────────────────────────────┘

2.3 核心设计 ​

  • 索引：Radix Tree（前缀 token 序列 -> KV 块位置），共享前缀共享节点，引用计数。
  • 分层存储：热 KV 在 HBM，温在 DRAM，冷在 SSD；按访问频率迁移；预取与 decode overlap。
  • 复用粒度：块级（PagedAttention block），命中整段前缀直接复用 KV、跳过该段 prefill。
  • 淘汰：LRU + 引用计数（共享节点不被误删）+ 容量水位触发淘汰。
  • 一致性：copy-on-write--某请求要"分叉"生成不同 token 时，复制该块再写，不影响其他引用者。
  • 传输：MLA latent / 量化 KV 减传输量；RDMA 直传 decode 实例。

2.4 追问 ​

  • "命中率不高时怎么办？" -> 池是开销（占内存 + 索引维护），命中率低时收益为负。需动态评估：命中率低于阈值则退化为不池化或缩小池。
  • "池容量怎么规划？" -> 按"热点文档/会话总 KV 量 × 命中预期"估，分层让冷数据下沉到便宜的 SSD。
  • "多实例一致性？" -> 全局索引 + KV 块不可变（写时复制），避免复杂一致性；跨实例只读共享。
  • "KV 池故障？" -> 命中失效退化为重新 prefill（可接受，非数据丢失）；索引持久化可加速恢复。

3.2 关键点 ​

  • MLA 适配：不能当普通 KV。需 latent cache 专用 kernel（上投影 c_KV->K/V + 解耦 RoPE 拼接）；调度器管理 latent 而非 K/V；TP 切分按 latent 维度调整。对照作者 GLM-5.2 Attention 机制。
  • MoE 适配：attention 仍 dense（KV Cache 正常），但 FFN 是专家路由。需 expert routing kernel + EP 通信（all-to-all）+ 负载均衡处理。权重显存大头是专家。
  • 权重分片：TP 切 attention 头 + latent；EP 切专家；PP 切层。三者组合。
  • 量化：权重 W8A8/FP8 + KV fp8（MLA 量化 latent）。
  • 验证：精度（对比 transformers 参考）+ 性能（Nsight profile kernel，对比基线）。

3.3 追问 ​

  • "MLA 的 TP 切分和普通 attention 有什么不同？" -> 普通 TP 切头，MLA 要切 latent 维度且保证上投影矩阵对齐，RoPE 部分单独处理。
  • "MoE 的显存瓶颈？" -> 专家权重（激活稀疏但权重全驻留），用 EP 分布到多卡；KV Cache 仍按 attention 算。
  • "MLA 在分离式推理下是优势还是劣势？" -> 优势：传输的是 latent（小），跨实例 KV 搬运量大幅减少。

题 4：优化线上推理成本 ⭐⭐⭐⭐ ​

4.1 杠杆点（按收益排序） ​

提利用率        ──►  连续批处理 / 大 batch / PD 分离按画像配比
减重算          ──►  前缀缓存 / RadixAttention / KV 池复用
减访存/显存     ──►  KV 量化(fp8/int4) / 权重量化 / 卸载分层
减串行步数      ──►  投机解码 / PD 分离
弹性            ──►  峰谷扩缩 / spot / 性价比芯片

4.2 量化收益 ​

  • 连续批处理 + PD 分离：goodput 提升 2-4x（典型）。
  • 前缀复用：命中场景 prefill 成本近归零（多轮/同文档）。
  • KV fp8：显存与带宽 2x，decode 吞吐 1.5-2x。
  • 投机解码：accept rate 高时步数减半。
  • 权重 INT4/FP8：显存 2-4x，可上更大 batch 或更小卡。

4.3 追问 ​

  • "哪个优化先做？" -> 先连续批处理 + 前缀复用（收益大、改动小），再量化，再 PD 分离（改动大、收益大）。
  • "量化精度掉了怎么办？" -> 敏感层保留高精度 + per-channel/FP8 + 评测对齐。
  • "投机解码什么时候不划算？" -> draft 接受率低、prefill 占比高、算力已打满时。

系统设计练习清单（自练） ​

每题限时 30min，画图 + 讲解，录音复盘：

  1. 设计支持百万 token 上下文的推理服务。
  2. 设计多模态（图+文）LLM 推理服务。
  3. 设计多 LoRA 适配器的 serving 服务。
  4. 设计跨地域的 LLM 推理平台（容灾 + 低延迟）。
  5. 设计一个推理引擎的调度器（优先级 + 抢占 + 显存）。

把每题的架构图存档，面试前快速过一遍。系统设计能力 = 练过的题量 × 反思深度。
